# bipe-api: agent notes

Bipe API: invite sign-up, device-first accounts and the handle directory (docs/usernames.md option A, ADR 0057). Contract: `../bipe-shared/api/openapi.yaml`. Change the contract first, then the code.

- Stack: Node 24, TypeScript, Hono, pg, Zod. pnpm only. Exact versions in package.json.
- Green gate: `pnpm build`.
- `src/generated/` comes from `../bipe-shared` (`pnpm gen`). Never edit it. Handle rules and normalisation live in bipe-shared and must match its test vectors.
- Runs on the dev node in Docker Compose (`../bipe-infra/compose`, service `api`, host `api.bipe.chat`). Postgres database `bipe` on the shared Postgres.
- MAS admin API: client_credentials with scope `urn:mas:admin`. The client ID and secret come from `.env` on the node; never log or print them. MAS cannot delete users: a failed sign-up deactivates the MAS user and refunds the invite use.
- Never log request bodies, emails, passwords, tokens or invite codes. Invite codes are stored only as SHA-256 hashes.
- Rate limits are in memory: one instance only.
- Admin CLI (in the container): `node dist/cli.js invite create --uses 10 --days 12 --note amigos`, `invite list`, `invite revoke <id>`, `invite grant @user:bipe.net.br 5` (extra personal invites), `invite revoke-user @user:bipe.net.br` (all pending invites of a user), `invite top --limit 50` (inviters ranked by joins: sent, joined, rate, downstream tree size and depth), `handle set @user:bipe.net.br <handle>` (staff: sets a handle without the 30-day cooldown; it still validates with the user as claimant, so an owned 2-character handle works only for its owner (ADR 0065), still puts the old skeleton on hold and still refuses a handle that another user holds or keeps on hold). The same report is `GET /v1/admin/inviters` for the page `bipe.chat/admin/convites/` (ADR 0056 in bipe/docs/adr): `StaffGate` lets only MAS admins through and answers `not_found` to everyone else.
- Personal invites (`/v1/me/invites`): `created_by` set, single use, 30 days. Pending invites hold a slot until they expire or are revoked; used invites hold it for `INVITE_RESPAWN_DAYS` (default 7) after the invitee joined, then it comes back. Quota = `INVITES_PER_USER` (default 10) + `invite_grants.extra`. Creation takes a per-user advisory lock so two requests cannot take the last slot.
- Handle change history (ADR 0066 in bipe/docs/adr): `setHandle()` and `removeHandle()` write a `handle_changes` row in the same transaction as the change (first set, change, removal; staff `handle set` with `source = 'staff'`). A handle chosen at sign-up is not recorded. Handle writes of one account take `pg_advisory_xact_lock(7140166, hashtext(user_id))`. `DELETE /v1/me/handle` puts the skeleton on hold and keeps the cooldown running from the last set (`old_set_at`). `POST /v1/handle-changes` returns changes for the Matrix IDs the app sends (max 100, optional `since`); it does not check room membership, like `resolve`, and never returns `source`. Retention: 365 days and the last 20 per account, pruned at startup and every 24 hours. Never log a handle next to a user ID.
- Profile change facts (ADR 0049 in bipe/docs/adr, bipe#598; `src/profile-facts.ts`): `POST /v1/profile-facts` returns, for the Matrix IDs the app sends (max 100), the account creation time (Synapse `users.creation_ts`) and the dates of name and photo changes in the last `windowDays` (`registries/profile-facts.json`); like `handle-changes`, it does not check room membership. Every 15 minutes `ProfileFacts.sync()` reads Synapse `profiles` (user_id, displayname, avatar_url) through `SYNAPSE_DATABASE_URL` and compares HMAC-SHA256(`BIPE_GROWTH_HMAC_SECRET`) digests in `profile_snapshots`; a new account gets its digests without a change. Both need the column grants on `profiles` and `users.creation_ts` in bipe-infra `scripts/setup-growth.sh`; without the secret or the URL the sync is off and the route answers with what it has. Public profile edits (`saveProfile` name change, `setPhoto`, `deletePhoto`) write a `profile_changes` row with `source = 'public'`. Dates only: never a name, an avatar URL or an image. Change rows go after `windowDays` (daily prune). Never log a user ID next to a change.
- Theft protection (ADR 0044, ADR 0051 in bipe/docs/adr, bipe#600, bipe#268; `src/theft.ts`): `GET`/`PUT /v1/me/guardians` (0 to `maxGuardians` of `registries/theft-protection.json`; the server checks only that a guardian is an account here and not the owner; the app offers verified contacts). `POST /v1/theft/{userId}/mark` by a guardian (else `not_found`): a `theft_marks` row, then MAS `lock`, then every active compatibility, OAuth 2.0 and browser session is finished. Accounts that sent the same phone ID (`PUT /v1/me/phone`, table `account_phones` with the device from the token) are covered: a personal account gets its own mark (`root_id`), a company account loses only that phone's sessions (ADR 0087). A MAS failure answers `internal` `theft_unavailable` and keeps the mark; a retry runs the steps again. `POST /v1/theft/{userId}/clear` by a guardian unlocks the mark and the accounts it covered. Clearing by CPF is not built (MZ decision on bipe#538): CLI `theft clear @user` after a CPF check by hand, `theft status @user`. `POST /v1/theft-marks` returns signed statements (bipe-shared `docs/theft-mark.md`, the badge key, `Badges.signTheft`); a marked account's badge answers 410 `stolen`. The MAS session filters and lock routes are unverified against a real MAS until `test/real` covers them. Never log a user ID next to a guardian.
- Phone links (bipe/docs/phone-link.md, ADR 0191 in bipe/docs/adr; `src/phones.ts`): lookup compares HMAC-SHA256(`PHONE_HMAC_SECRET`, E.164). `phone_links.number_enc` keeps the owner's own number, AES-256-GCM under HKDF-SHA256(`PHONE_HMAC_SECRET`, info `bipe phone number at rest v1`), written by `linkPhone` (CLI `phone link <user_id|@handle> <number>`: `existingAccount()` in `src/handles.ts` resolves an @handle and refuses an ID on another server or with no live MAS account). Only `GET /v1/me/phone` (the caller's own link) and the data export return it; lookup returns only the number the caller sent. Links made before the column have no number. A rotation of the secret must re-encrypt `number_enc` with the HMACs. Never log a number.
- `GET /v1/me/invite-connections`: the caller's invite pairs (people they invited who joined, plus their inviter). Clients skip Pedidos for DM invites from these users (ADR 0034 in bipe/docs/adr).
- `GET /v1/invites/{code}` is public with CORS for `PUBLIC_SITE_URL` (the invite page reads it). It never says why a code is invalid.
- `GET /v1/web/convite/{code}` (bipe#459, `src/invite-preview.ts`) returns an HTML head for link-preview crawlers. The edge (bipe-infra Caddyfile, both configs) sends only crawler user agents here; browsers get the static page. It shows the public profile name and photo, else the handle, else the generic card. The image URL never holds the code, and the page never says why a code is invalid.
- `POST /v1/waitlist` (ADR 0025) is public with CORS for `PUBLIC_SITE_URL`. It answers 202 for every well-formed request, duplicates and the `website` honeypot included, so it never tells whether an address is known. Admin CLI: `waitlist count`, `waitlist export android`, `waitlist clear android` (after the launch email), `waitlist forget <email>`. Release (ADR 0089): `waitlist release ios --count 20 [--days 14]` gives the oldest uninvited entries one single-use invite each (note `waitlist-YYYY-MM-DD`) and mails `/convite/<code>`. It refuses when email is off. A failed send revokes that invite and puts the entry back. The server deletes an entry every 24 hours once its invite is used, expired or revoked. Release only a platform with a public build.
- Organisation requests (ADR 0126, bipe#410, bipe#273): the site's organisation form posts to the Bipe workspace on Starlings. The API has no route, table or CLI for them; a migration dropped `organisation_requests` when it was empty.
- `POST /v1/events` (ADR 0032) counts headline-test events as daily aggregates: no IP, no identifier. The site sends it with `sendBeacon` (text/plain JSON, no CORS). Report: `node dist/cli.js experiment report headline-77`. Run the report before `waitlist clear`: sign-ups per arm come from waitlist rows.
- Growth events (ADR 0098, bipe#67; `src/growth.ts`): the apps send no telemetry. The event list is `../bipe-shared/registries/growth-events.json`. Table `growth_events`: one row per user, event and day with a count; the user is HMAC-SHA256(`BIPE_GROWTH_HMAC_SECRET`, Matrix ID). Never rotate that key: every user becomes a new pseudonym. API events: `signup_done` and `invite_redeemed` in `createAccount()` (a replay does not count), `onboarding_finished` on the first `GET /v1/me/account`, `invite_sent` on `POST /v1/me/invites`. Synapse events: every 15 minutes, `growth.sync()` reads the Synapse database through `SYNAPSE_DATABASE_URL` (role `bipe_growth`, column grants only, bipe-infra `scripts/setup-growth.sh`). A new Synapse column in a query needs a grant there first, or the sync fails with "permission denied". Platform events (`platform_ios`, `platform_android`, `platform_web`): `syncPlatforms()` reads Synapse `devices` (user_id, user_agent, last_seen), `platformOf()` maps the user agent to a platform, and only the platform is kept. `contact_fifth` (bipe-chat/bipe#752): `syncFifthContacts()` finds DM-shaped rooms (2 joined, 0 invited, no name, not a space, member events from exactly 2 local people) with the granted columns only and keeps the day of each user's fifth contact; `growthNumbers().contacts` gives median and p75 days per sign-up week, with invites accepted per member. `growth_sync` keeps the read positions. Rows older than `retentionDaysKept` are deleted. Report: `node dist/cli.js growth report [--since YYYY-MM-DD]` (it syncs first). Never log a user ID or a uid.
- Visit report (ADR 0098; `src/visits.ts`): `GET /v1/admin/visits?days=30` for the page `bipe.chat/admin/visitas/`, behind `StaffGate`. It reads Umami through `UMAMI_DATABASE_URL` (role `bipe_growth`, column grants on `session` and `website_event` only, bipe-infra `scripts/setup-growth.sh`). Country BR only, by state (`region` without `BR-`) and city, top 200 cities. Without the URL the route answers `internal`.
- Strategic pages (ADR 0157, ADR 0158 in bipe/docs/adr; `src/proposta.ts`): `bipe.chat/proposta/` takes any well-formed email and one shared password. The email only names the visitor in the log (`proposta_visitors`, made on the first sign-in); nobody checks it. The edge sends `/proposta/_auth/*` to `/v1/proposta/*`, so cookie `bipe_proposta` (Path `/proposta`, HttpOnly, Secure, 30 days) belongs to bipe.chat, and asks `GET /v1/proposta/check` before each request (Caddy `forward_auth`, bipe-infra both Caddy configs). A page GET writes a `proposta_visits` row (path, referrer origin, `utm_*`, GeoIP place; no IP, no user agent); the deck sends each slide to `/v1/proposta/beacon`. The password is one scrypt hash in `proposta_password` (`hashPassword()`, no pepper); without it every sign-in is 401. bipe-infra `scripts/setup-proposta.sh` sets it from the Keychain with `proposta password --password-stdin`, which ends every session. Visits go after 365 days. Time per slide and summaries (ADR 0160): the pages send `event: leave` when the tab is hidden or closed; a sitting is one visitor's events with gaps under 30 minutes; a step's time is the gap to the next event, at most 10 minutes. Every 5 minutes `sendSummaries()` emails one plain-text summary per sitting that ended 30 minutes to 24 hours ago to `PROPOSTA_NOTIFY_EMAIL` (off when unset or when email is off); the `proposta_summaries` row goes in before the send and a failed send deletes it. Staff: `GET /v1/admin/proposta?days=30` (with `sittings`); CLI `proposta password`, `visits`, `sessions`, `forget <email>`. Never log an email next to a path.
- Growth report for staff (bipe#373): `GET /v1/admin/growth?since=YYYY-MM-DD` (default 90 days) for `bipe.chat/admin/crescimento/`, from `growthNumbers()` (the CLI `growth report` formats the same numbers). Never returns or accepts a uid.
- First-contact outcomes (security.md rule 11, bipe#845; `src/reach.ts`, windows in `registries/reach.json`): when `mayInvite` allows an invite that is a first contact (no shared joined room, no invite pair; the support and news bots never count), `Reach.record()` writes a `first_contacts` row: inviter, `invitee_hash` (HMAC-SHA256 under HKDF-SHA256(`BIPE_GROWTH_HMAC_SECRET`, info `bipe reach invitee v1`), so it never equals the growth pseudonym), room and time. The Synapse module `bipe_messaging` (bipe-infra) sends `room_id` with `may-invite`, and calls `POST /internal/v1/first-contacts/membership` (the invitee's join = accepted, the invitee's own leave = declined; the first outcome sticks) and `POST /internal/v1/first-contacts/ignored` (both answer `{}`: the module client parses JSON; a new `m.ignored_user_list`; an ignored inviter of a first contact in the last `blockWindowDays` = blocked, once per inviter). Those calls never block the event: the module logs and drops a failure. Every 15 minutes `syncReports()` reads new Synapse `event_reports` (id, received_ts, event_id) with `events` (event_id, sender) and counts each report against the local sender (`reach_state` keeps the read position; both `event_id` columns need the grant in bipe-infra `setup-growth.sh`). Every hour `prune()` deletes first contacts older than `recipientDays`, counting one with no outcome and no block as ignored, and daily counts older than `dailyCountDays`. `reach_daily` holds per-sender counts per day in Brazil: `sent`, `accepted`, `declined`, `ignored`, `blocked`, `reported`. Staff: CLI `reach show <@user|@handle> [--days 30]`; `/v1/admin/retention` item `first-contacts`. The export leaves out the hash and folds blocked into `not_answered` (a block is the recipient's private choice). Off without `BIPE_GROWTH_HMAC_SECRET`. Never log a user ID next to an outcome.
- Minimum cell size (bipe#371, `src/staff-report.ts`): `MIN_CELL` is 3. Staff routes return null for a count of 1 or 2, hide sign-up weeks below it, and fold small cities into one row per state. Every new aggregate staff route uses `cell()`.
- Read-only staff reports (bipe#368, `src/staff-reports.ts`), all behind `StaffGate`: `GET /v1/admin/experiments` (#376), `/waitlist` (#374, no email), `/business` (#375, same rows as `business list`), `/reports?days=90` (#380, Synapse `event_reports`: room, reason, score; needs the grant in bipe-infra `setup-growth.sh`), `/retention` (#381, rows past each data item's limit). New staff routes use `staffGet()` in `server.ts`.
- Staff index (bipe#394): `GET /v1/admin/summary` for `bipe.chat/admin/`, from `StaffReports.summary()`. One object per staff page key. Each part runs alone: an off or failed source gives null for that page, not a 500. Counts of people go through `cell()`. A new built staff page with a number gets a part there and in the contract `StaffSummary`.
- Staff dashboard: `GET /v1/admin/metrics?days=91` for `bipe.chat/admin/`, from `StaffReports.metrics()`. Daily series and 7-day windows in Brazil time; rates come from raw counts, counts go through `cell()`. A null in a live series column (see `sources`) is a count below `MIN_CELL`, not an off source.
- CNPJ verification (ADR 0042 in bipe/docs/adr, docs/cnpj-verification.md): `/v1/me/business*`. The registry is the Receita release on disk (`RECEITA_DIR`, host `compose/data/receita`), scanned for claimed CNPJs only; never bulk-import it (4 GB node). e-CNPJ proof needs the pinned roots in `certs/icp-brasil/` (`ICP_BRASIL_ROOTS_DIR`); without them the route answers `internal` with reason `icp_brasil_roots_missing`. Never store a signature or a certificate. CLI: `registry fetch [YYYY-MM]`, `registry scan [--all]` (run `--all` after each monthly fetch), `business list`, `business claim @user <cnpj>` (staff: starts the claim like `POST /v1/me/business`, runs the scan when the CNPJ is not in the registry copy yet), `business verify @user`, `business revoke @user`. One scan at a time (advisory lock 7140142).
- CVM register check (ADR 0077, bipe#237; `src/cvm.ts`): once a day (`startCvmRefresh`, off with `CVM_REFRESH=false`) the server downloads the seven provider registers and `ato_declr.csv` from dados.cvm.gov.br (latin1, `;`, CRLF; zips read from their central directory) and replaces `cvm_registrations` and `cvm_stop_orders` in one transaction. A failed download or an unknown file shape keeps the last good tables (a stop order stays flagged), writes `cvm_state.last_error` and logs `cvm: ALERT`. Column names and `SIT` values follow ADR 0077 and are unverified against the live files until the first real refresh. The Receita scan stores `cnae_main` and `cnae_secondary` for the financial CNAE rule (divisions 64 to 66). `cvmField()` gives the signed badge field `cvm` (bipe-shared `docs/badge-attestation.md`): `stop_order` overrides, then `registered` with the categories, then `cancelled` with the newest date, then `no_registration` for a financial CNAE only; a table older than 7 days gives no field. Stop orders without a CNPJ are not matched (no CPF, no names). CLI `cvm refresh`, `cvm status`, `cvm show <cnpj>`. Attribution "Fonte: CVM, dados.cvm.gov.br" is in the apps.
- gov.br signed challenge, trust step 5 (bipe#543, `src/govbr.ts`, shared CMS check in `src/cms.ts`): `POST /v1/verifications/govbr` makes a one-page PDF (handle, date, code `XXX-XXX`, also in `/Keywords` as `bipe-govbr:<code>`), single use, 30 minutes, bound to the caller's device Ed25519 key from Synapse `e2e_device_keys_json` (needs the bipe-infra `setup-growth.sh` grant; without it the route answers `internal` `device_key_unavailable`). `PUT /v1/verifications/govbr/{id}/document` (PDF, 5 MB) checks the signature that covers the whole file against the pinned roots in `GOVBR_ROOTS_DIR` (`certs/govbr`, AC Raiz do Governo Federal do Brasil v1 and intermediates; not ICP-Brasil; missing: `internal` `govbr_roots_missing`), finds the code, reads name and CPF from the signer certificate and writes `person_verifications` (name, level, device key, HMAC-SHA256 of the CPF with `BIPE_CPF_HMAC_SECRET`; never rotate it). A rejection is 200 with `state: rejected` and `reason`, and leaves the challenge open. `cpf_in_use` comes from the unique hash. Never store or log the PDF, the CPF or the certificate. CPF location and code survival are best guesses until bipe#542; a certificate without a readable CPF answers `internal` `govbr_cpf_missing`. Badges: no verified company claim means a person badge (`lvl` `pix` or `govbr`, `dev`) from `person_verifications`. Challenges are pruned a day after they expire.
- Receita's WebDAV share answers 200 with an empty body unless the request has a PROPFIND body and a browser-like user agent.
- Public profiles (ADR 0041 in bipe/docs/adr): `GET /v1/profiles/{handle}` and its `/photo` are public with CORS for `PUBLIC_SITE_URL`, exact handle only, and answer the same 404 for "no handle" and "profile off". `PUT /v1/me/profile/photo` takes a JPEG up to `photoMaxBytes` (the only route with a larger body limit). `stripJpeg()` drops every APPn and COM segment and fails closed on anything it cannot parse. Photo URLs use `PUBLIC_API_URL`. A verified company's profile carries the same `badge` envelope as `GET /v1/badges/{userId}`; a badge failure omits it and never hides the profile.
- Badges (bipe#399, ADR 0123 in bipe/docs/adr; `src/badges.ts`, format `../bipe-shared/docs/badge-attestation.md`): `GET /v1/badges/{userId}` is public (CORS for `PUBLIC_SITE_URL`, 120 per IP per minute). No badge store: the API signs on read and caches the envelope in memory until `renewDaysBeforeExpiry` before `exp` (`registries/badge-keys.json`, life 7 days). Only a `verified` claim with an active registry record gets one: `lvl` `cnpj`, bound to the account's cross-signing master key (`msk`), read from Synapse `e2e_cross_signing_keys` (newest `master` row by `stream_id`) through `SYNAPSE_DATABASE_URL` (needs the bipe-infra `setup-growth.sh` grant). A `revoked` claim answers 410 `{reason}`. Everything else answers 404: no claim, no master key, no Synapse URL, no key. The key is `key.pem` and `kid` in `BIPE_BADGE_KEY_DIR` (Secret `bipe-badge-key`, bipe-infra `scripts/setup-badge-key.sh`); never log, print or copy it. A kid that is not in `registries/badge-keys.json` still signs, and the start log says the apps reject it.
- Invite codes: `extractInviteCode()` finds the code in a bare code, a link or a pasted message. It must pass `../bipe-shared/test-vectors/invite-codes.json` (iOS and Android pass the same file).
- Device-first accounts (ADR 0057, ADR 0059 in bipe/docs/adr; `src/accounts.ts`, `src/secrets.ts`, `src/mailer.ts`):
  - `POST /v1/signup` without `password` is device-first: the API makes a random 32-byte password, sets it through the MAS admin API and returns it once with a 32-byte recovery token. It never stores or logs the password; it stores only the SHA-256 of the token. Email is an optional recovery fallback in `recovery_emails`, never given to MAS. With `email` and `password` it is the old beta sign-up (MAS login email and own password).
  - PIN: `pinProblem()` from bipe-shared (`registries/accounts.json`, `test-vectors/pins.json`). Hash: scrypt (N 2^15, r 8, p 1, 16-byte salt, 32-byte key) over HMAC-SHA256(key `BIPE_PIN_PEPPER`, PIN), stored as `scrypt1$salt$hash`. The pepper is only in the environment. Without it the PIN routes answer `internal`. `verifyPin()` locks the row, so parallel tries cannot pass `pinMaxWrongTries` (5, in total over every path). A correct PIN sets the count to 0. A blocked PIN refuses even the right PIN until a reset.
  - Every recovery path checks its other factor first, then the PIN (ADR 0059): `POST /v1/recovery/token` (synced token + PIN, no delay, new password and token), `POST /v1/recovery/email` (link, always 202), `.../email/confirm` (link + PIN for access, or a new PIN for a reset; starts the 24-hour delay), `POST /v1/recovery/{id}/claim` (claim secret; after the delay it returns new credentials once, or applies the new PIN). Old devices read waiting recoveries in `GET /v1/me/account` and cancel with `POST /v1/me/recoveries/{id}/cancel`. Guardian and CPF recovery are not built (no guardian store, no Pix verification yet).
  - Sign-up retry (ADR 0094): `signup_key` in `POST /v1/signup` (device-first only). The same key returns the same account and creates nothing; `POST /v1/signup/resume` returns it with only the key. `signup_replays` keeps the key's SHA-256 and the password and token sealed with AES-256-GCM under HKDF-SHA256(key). The row goes on the account's first `GET /v1/me/account`, on a failed sign-up and after 7 days. Two tries with one key at once: the second gets `rate_limited` with reason `signup_in_progress` (an in-memory set; one instance only). Replay runs before the attestation check.
  - Android Key Attestation (bipe#92, `src/key-attest.ts`, README "Android Key Attestation policy"): `attestation.key_attestation_chain` is checked against the pinned Google roots in `certs/google-key-attestation-roots.pem` (from `https://android.googleapis.com/attestation/root`; update them together when Google adds a root) and Google's revocation list (refreshed every 6 hours). A forged or foreign chain is `attestation_invalid`. A genuine chain from a phone that is not attested (software keystore, unlocked, boot not verified, no revocation list yet) counts as no attestation, so sign-up stays open (ADR 0043). Never log a chain.
  - Sign-up limits (`src/signup-limits.ts`, bipe#395): attempts per IP, 5 per hour without an attestation, 30 with one (CGNAT: many phones share one IP), checked before any proof. Account creations in total, `SIGNUP_MAX_PER_HOUR` (default 30): `createAccount()` takes one only after the attestation, terms, PIN and invite checks pass, and gives it back when the sign-up fails. Rejected attempts never use a creation. A replay takes none. The edge must pass the real client IP (bipe-infra `k8s/bipe/edge.yaml`, `{client_ip}`).
  - Signed-in device: `PUT /v1/me/pin` (no old PIN: the app asks for a biometric check first, ADR 0057), `POST /v1/me/pin/check`, `POST /v1/me/device-first` (beta account to hidden password, needs a PIN), `POST /v1/me/recovery-token`, `PUT`/`DELETE /v1/me/email`. `POST /v1/email/verify` is public with CORS for `PUBLIC_SITE_URL`.
  - Links: `PUBLIC_SITE_URL/recuperar/#<token>` and `/confirmar-email/#<token>`. The token is in the fragment, so it stays out of web server logs.
  - Outgoing email: `BIPE_SMTP_HOST` (empty: email off, the email routes answer `email_unavailable`), `BIPE_SMTP_PORT` (465 implicit TLS; any other port must offer STARTTLS, else the send fails: never plain text), `BIPE_SMTP_USER`, `BIPE_SMTP_PASSWORD` (AUTH PLAIN after TLS), `BIPE_MAIL_FROM`. Certificates are checked. Mail text comes from bipe-shared strings `bipe_mail_*`. Sends run in the background; a failure logs the SMTP reply code only, never the address.
  - One sender (ADR 0166): every Bipe email goes through `Mailer` in `src/mailer.ts` and the `BIPE_SMTP_*` relay (SMTP Locaweb). Do not add a mail library, a second SMTP client or a mail API (Resend, SES, Cloudflare Email) here or in another Bipe repo. A service that needs to send mail asks bipe-api to send it; it gets no SMTP credentials of its own. MAS keeps `email.transport: blackhole`; Synapse has no `email:` block.
  - Transfer readiness (bipe#531, `src/transfer.ts`, bipe/docs/team-transfer-recovery.md): `POST /v1/me/keychain-move` records that an iPhone copied its keychain items into the app-group keychain group (table `keychain_moves`, one row per user and device; the device comes from the token, never the body). `INDEPENDENT_RECOVERY_USERS` is the one rule for a factor that does not depend on the Apple Team ID (a verified recovery email or a linked Google account; never Apple, whose `sub` changes with the team); `GET /v1/me/account` returns it as `independent_recovery`. Staff: `GET /v1/admin/transfer-readiness?days=30` and CLI `transfer report [--days N]`, counts through `cell()` only. It reads Synapse `devices` (user_id, device_id, user_agent, last_seen): `device_id` needs the column grant in bipe-infra `scripts/setup-growth.sh`.
  - Checked against real MAS 1.26.0 (2026-10-21, `test/real/accounts.real.test.mjs`): MAS keeps the old device's sessions when the admin API sets a new password, and the MAS admin `user-emails` resource has `attributes.user_id`.

## Before you push

- CI must stay green. `scripts/verify` runs what the required checks of the `main` ruleset run. Run it before every push; the pre-push hook runs it when this clone has `git config core.hooksPath .bipe-hooks` (set it once per clone; worktrees share it).
- A push with red local checks is not allowed. Never use `git push --no-verify`.
- If CI still fails on your pull request, fix it before you start other work. Never leave a red pull request at the end of a run.
